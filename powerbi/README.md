# Power BI Dashboard — UPI Fraud & Merchant Risk Analytics

Native Power BI Project (`UPI_Fraud_Analytics.pbip`) built directly on the
cleaned star schema in `../data/cleaned/`. Generated by
[`../scripts/build_powerbi_project.py`](../scripts/build_powerbi_project.py) —
rerun that script any time the cleaned data or design changes, then reopen the
`.pbip` in Power BI Desktop. **The script overwrites files under `powerbi/`
in place; it does not delete the folder first.** Don't `rm -rf powerbi/`
before rerunning it — this file and anything else placed loosely under
`powerbi/` (rather than inside `.Report`/`.SemanticModel`, which the script
owns) survives a rerun only if the folder itself isn't deleted first.

This document explains **what was done to the raw data**, and **every KPI,
plot, filter, and design choice** in the report, with why it was included.

---

## 1. What was done to the datasets (processing pipeline)

Raw files (`data/raw/`, not published — see root `README.md`) go through
[`scripts/clean_pipeline.py`](../scripts/clean_pipeline.py) →
[`scripts/compute_metrics.py`](../scripts/compute_metrics.py) →
this Power BI project. Full before/after counts are in
[`../reports/data_quality_report.md`](../reports/data_quality_report.md); every
normalization rule is in
[`../reports/cleaning_mapping_reference.md`](../reports/cleaning_mapping_reference.md).
Guiding rule throughout: **never silently drop a messy row** — standardize it,
and if the raw value can't be trusted, flag it with an explicit boolean column
instead. Rows are only removed for exact duplication or a fully unrecoverable
ID.

### `track1_upi_transactions.csv` → `fact_transactions` (20,000 rows)
- Standardized `user_id` / `merchant_id` / `txn_id` formats (`USR12345`,
  `usr-12345`, `12345`, …) to one canonical prefix + fixed digit width.
- Cleaned `amount`: stripped ₹/Rs/INR and thousands separators; 420 negative
  values were sign-corrected (kept, not dropped) and flagged
  `amount_was_negative`.
- Parsed 6+ mixed timestamp formats (epoch seconds, ISO, day-first slash,
  month-first dash, etc.) into one consistent datetime.
- Normalized `status` spellings (`Success`/`TXN_SUCCESS`/`COMPLETED` →
  `SUCCESS`, etc.).
- Cleaned `utr`: valid only if exactly 10 digits after stripping
  spaces/hyphens; 1,000 rows had a missing UTR (flagged `utr_missing`, kept).
- Removed 400 exact-duplicate rows; 0 additional duplicate `txn_id` after
  standardization.
- Added `user_id_valid_fk` / `merchant_id_valid_fk`: **13,522 transactions
  reference a `user_id` not in the KYC master, 10,369 reference an unknown
  `merchant_id`** — kept and flagged rather than dropped, because this turned
  out to be the dataset's headline finding, not noise (see §6, Data Quality).

### `track1_kyc_records.csv` → `dim_customers` (28,920 rows, from 36,400 raw)
- Standardized `user_id`; collapsed 7,480 duplicate `user_id` rows (kept the
  most complete record, tie-broken by most recent signup).
- Validated PAN (`AAAAA9999A` pattern) and Aadhaar (12 digits); both are
  **masked** in the published output (first/last characters only) even though
  the data is synthetic, since this repo is public.
- Cleaned `monthly_income`: currency symbols, `k`/`l` (lakh) suffixes; 1,210
  negative values sign-corrected; 3,057 left null and flagged where
  unparseable.
- Consolidated city spellings/abbreviations (`bombay`/`MUMBAI`/`mumbai` →
  `Mumbai`, etc.) and normalized `kyc_status` / `risk_segment` spellings.

### `track1_merchants_master.csv` → `dim_merchants` (4,343 rows, from 6,210 raw)
- Standardized `merchant_id`; collapsed 1,867 duplicate rows.
- Normalized 82 raw category spellings into 10 canonical `merchant_category`
  values.
- Cleaned MCC codes (bare/zero-padded/float/hyphenated/`misc`) to a 4-digit
  string; 367 missing codes imputed from the modal MCC for that merchant's
  category and flagged `mcc_imputed`.
- 349 negative `declared_avg_ticket_size` values sign-corrected and flagged.

### `track1_chargebacks.json` → `fact_chargebacks` (2,800 rows, from 2,884 raw)
- Parsed JSON, standardized `txn_id`/`user_id`/`merchant_id` formats.
- Consolidated 33 raw reason-code variants into 7 canonical categories
  (original text kept in `reason_code_raw`).
- Normalized `severity` (P1–P4 → Critical/High/Medium/Low), `resolution_status`,
  `channel`.
- Flagged 108 chargebacks with **logically impossible timestamps** (bank
  response before reported, or reported before the transaction itself) —
  kept, excluded only from the delay-days average, not from counts.
- Added `txn_id_valid_fk` / `user_id_valid_fk` / `merchant_id_valid_fk`: 193
  chargebacks reference an unknown transaction, 1,915 an unknown user, 1,501
  an unknown merchant.

### Data model built from the cleaned tables
Star schema: `dim_customers` / `dim_merchants` (1) → `fact_transactions` /
`fact_chargebacks` (many), plus a conformed `DateTable`. The
`fact_transactions` ↔ `fact_chargebacks` link (on `txn_id`) is set **inactive**
— both fact tables already reach `dim_customers`/`dim_merchants` directly on
`user_id`/`merchant_id`, so an active link on top would create an ambiguous
second filter path between the same two tables, which Power BI disallows as
active simultaneously. `TxnDate`/`ReportedDate` (computed in Power Query, not
DAX) give `fact_transactions` and `fact_chargebacks` each their own link to
`DateTable` as a role-playing date dimension — calculated *tables/columns* are
deliberately avoided as relationship endpoints; see the note in
`scripts/build_powerbi_project.py` for why (a real bug hit during this build:
`PFE_TM_RELATIONSHIP_END_COLUMN_INVALID`, caused by exactly that).

## 2. KPIs (DAX measures), grouped by category, with significance

**Transaction KPIs**
- **Total Transactions / Total Txn Amount** — overall volume and value; the
  base denominator for every rate below.
- **Total Txn Amount (Success)** — money that actually moved, vs. attempted —
  the number a finance stakeholder actually cares about.
- **Avg Txn Value (All / Success)** — typical ticket size; a large gap between
  the two flags failed/pending transactions skewing the average.
- **Success / Failed / Pending Rate** — the transaction funnel in one glance;
  a rising failed rate is an early operational-health signal, independent of
  fraud.
- **Transactions Missing UTR / Invalid UTR (+ combined Missing/Invalid UTR
  Rate)** — a missing settlement reference is itself a fraud/reconciliation
  signal, not just a data-quality nit (per the dataset notes: "missing UTRs
  may correlate with failed/disputed transactions").
- **Txn Volume Trend / Txn Value Trend / Success Rate Trend / Failed Rate
  Trend** — text measures (`▲ 12.3% vs 1st half`) comparing the second half
  of the observed window against the first half. This is the Power BI
  analogue of the HTML dashboard's mini trend-delta badges. It's deliberately
  a first-half/second-half split, not a "vs last month" comparison — the
  model has no marked date table or time-intelligence functions set up (see
  §1), so this is the honest comparison the data actually supports.

**Chargeback & Dispute KPIs**
- **Chargeback Count / Amount** — raw dispute exposure, by volume and by ₹.
- **CB to Txn Ratio (Count / Amount)** — the core fraud-rate KPI; reported both
  ways because a low count-ratio can hide a high amount-ratio (a few
  high-value disputes).
- **Avg Dispute Delay (Days)** — how long customers take to report a problem;
  computed only over logically-valid timestamps so the 108 broken-sequence
  rows don't distort it.
- **Disputes Reported After 7d (+ Rate)** — per the dataset notes, a long
  reporting delay can indicate **account takeover or late fraud detection**,
  not just a slow customer.

**Risk KPIs**
- **Merchant CB to Txn Ratio** — dispute rate per merchant, restricted to
  merchants with a valid master-data match so the ratio isn't distorted by
  unmatched-ID noise.
- **High Risk Users (2+ Disputes) / High Risk Merchants (2+ Disputes) / Users
  With Disputes** — operationalizes "high-risk user/merchant" as a countable
  KPI instead of a vague label; the merchant version mirrors the user one
  exactly (2+ chargebacks against that ID).
- **CB on Unmatched Merchant (Count / Amount)** — chargebacks tied to a
  merchant ID with **no master record at all** — a distinct risk category from
  "known merchant, high ratio."
- **Merchant-Day Spikes (2+ Txns)** — count of merchant-days with 2+
  transactions, anomalous against this population's ~1-transaction-per-90-days
  norm; backed by the `MerchantSpikeDays` calculated table (§3, Page 4) for
  the actual list of which merchants/days.

**KYC & Merchant KPIs**
- **KYC Completion Rate / Rejection Rate** — the KYC funnel; a low completion
  rate directly limits how much of the platform is even identity-verified.
- **Total Customers / Total Merchants** — base population sizes, for context
  behind every rate above.

**Data Quality / Join Integrity KPIs** (surfaced as first-class KPIs, not a
footnote — see the dataset's own headline finding)
- **Txn User FK Match Rate (32.4%) / Txn Merchant FK Match Rate (48.2%)** — the
  share of transactions that actually link to a real identity/merchant record.
  This is low enough that it changes how every other KPI on the report should
  be read: most of the platform's activity has no linkable identity at all.
- **CB Txn FK Match Rate** — the share of chargebacks that tie back to a real,
  recorded transaction (93.1%) — the 6.9% that don't are disputes with no
  underlying transaction on file, a red flag in themselves.

## 3. Plots / visuals used, grouped by page, with significance

**Page 1 — Overview**
- **4 KPI cards** (Total Transactions, Total Txn Amount, Success Rate,
  Chargeback Count) — the single-glance headline numbers, always visible
  regardless of which filter is applied. Chargeback Count carries the
  risk-elevation card style (see §5) since it's the one fraud-signal number
  on an otherwise volume-focused page.
- **4 trend-delta cards** directly beneath them — the ▲/▼ vs-first-half read
  on each headline number, so direction of travel is visible without opening
  a chart.
- **Daily Transaction Count** (line) — volume trend over the 3-month window;
  spikes/drops are the first thing an analyst checks.
- **Daily Transaction Value** (line) — kept as a *separate* chart from count
  rather than a dual-axis combo — a dual-axis chart is easy to misread; a big
  count doesn't imply a big value if ticket sizes differ.
- **Transaction Amount by Merchant Category** (column, drillable to Merchant
  Name) — answers "which categories drive revenue," and lets you drill into
  exactly which merchant within a category is responsible.

**Page 2 — Fraud & Dispute Analysis**
- **4 KPI cards** (Chargeback Amount, CB-to-Txn Ratio, Avg Dispute Delay,
  Disputes After 7d) — the dispute-side headline numbers, all carrying the
  risk-elevation card style (crimson border, light-red tint) since this whole
  page is the active-fraud-exposure page.
- **Chargeback Reason Distribution** (donut) — which fraud/dispute category
  (account takeover, unauthorized transaction, duplicate debit, …) dominates —
  directly actionable for prioritizing fraud-prevention work.
- **Chargeback Severity Distribution** (donut) — Critical/High disputes need a
  different response SLA than Low; this shows the mix at a glance.
- **Merchant CB-to-Txn Ratio by Category** (bar) — which merchant *categories*
  carry disproportionate dispute risk, independent of any one outlier
  merchant.
- **Top Merchants by Chargeback Exposure** (table) — the actual named
  merchants driving dispute count/amount — the "who do we call first" list.

**Page 3 — Customer Risk & Data Quality**
- **4 KPI cards** (KYC Completion Rate, KYC Rejection Rate, Txn-KYC Match
  Rate, Txn-Merchant Match Rate) — KYC funnel + the join-integrity numbers,
  deliberately on the same page so low match rates are read alongside KYC
  health, not hidden on a separate page. Kept in the neutral card style (not
  risk-elevated) — these are data-quality/funnel measures, not "active fraud"
  signals.
- **KYC Status Distribution** (donut) — Verified/Pending/Rejected mix.
- **Transactions by Customer State** (bar, drillable to City) — geographic
  concentration of activity.
- **Users by Chargeback Count** (table) — sortable list to find repeat-dispute
  customers, including ones with **no KYC record at all** (a specific
  fraud-ring pattern called out in the root README).

**Page 4 — Fraud-Ring Spotlight** (mirrors the HTML dashboard's "Fraud-Ring
Spotlight" section; added to close specific evaluation-note gaps — see below)
- **3 KPI cards, neutral style** (Pending Rate, Failed Rate, Avg Txn Value) —
  these existed as measures already but had no card anywhere in the report;
  this page is where they're surfaced.
- **3 KPI cards, risk-elevation style** (Missing/Invalid UTR Rate, High Risk
  Merchants (2+ Disputes), Merchant-Day Spikes (2+ Txns)) — all three are
  fraud/anomaly signals, not routine funnel numbers.
- **Top Merchants by Disputed Amount** (table: merchant, category, chargeback
  count, chargeback amount) — sort by the Chargeback Amount column for the
  ranked answer to "top merchants by disputed amount."
- **Merchant Same-Day Transaction Spikes** (table, from the new
  `MerchantSpikeDays` calculated table) — every merchant-day with 2+
  transactions: the actual named "suspicious transaction clusters" /
  "merchants with sudden transaction spikes," not just a count. Built via
  `SUMMARIZE` + `FILTER` + `ADDCOLUMNS`/`LOOKUPVALUE` (not `RELATED`) so its
  columns are never a relationship endpoint — see the model note in §1.
- The page's own rail filters (Merchant Category, Merchant Status, Merchant
  Dispute Risk, Merchant Spike Day) let you combine, e.g., "show only Active
  merchants flagged Repeat (2+) Disputes" to actually enumerate the high-risk
  merchants behind the count card, the same pattern as Page 3's user-risk
  filters.

## 4. Filters, grouped by KPI category, with reasoning

**Global (present on every page)**
- **Date** (`DateTable[Date]`) — every KPI group has a time dimension.
- **Merchant Category** — the single most-repeated cut across the dataset
  notes' example questions; applies to Transaction, Chargeback, and Risk KPIs
  alike.

**Page 1 — Transaction KPIs**
- **Transaction Status** — isolate SUCCESS/FAILED/PENDING instead of reading
  it off a stacked chart.
- **UTR Problem? (one-click, derived)** — combines `utr_missing OR NOT
  utr_valid` into one flag; one click tests whether UTR trouble correlates
  with failed/disputed transactions across every visual on the page.

**Page 2 — Chargeback & Dispute KPIs**
- **Reporting Delay Bucket (one-click, derived)** — bins `reporting_delay_days`
  into Same-day / 1–3 / 4–7 / 8+ days, turning "average delay is 6.5 days"
  into "how many are in the worst bucket" — the account-takeover signal.
- **Timestamps Logically Valid** — flip to see *only* the impossible-timestamp
  disputes your delay KPI silently excludes.
- **Resolution Status**, **Channel** — named KPIs/example questions in the
  dataset notes; each earns its own slicer rather than being buried in a
  chart.

**Page 3 — Risk / KYC / Data Quality**
- **KYC Status**, **Risk Segment** — the KYC funnel and assigned risk band.
- **Customer Dispute Risk (one-click, derived)** — buckets every customer into
  Repeat (2+) / Single / No Disputes; this *is* the "High-Risk Users" KPI as a
  clickable filter instead of a sorted table.
- **Merchant Spike Day (one-click, derived)** — flags merchants that ever had
  2+ transactions on the same calendar day; isolates exactly the "Fraud-Ring
  Spotlight" merchants the root README calls out as the headline finding.

**Page 4 — Fraud-Ring Spotlight**
- **Merchant Category**, **Merchant Status** — same reasoning as elsewhere,
  scoped to the merchant-risk page specifically.
- **Merchant Dispute Risk (one-click, derived)** — the merchant-side twin of
  Page 3's Customer Dispute Risk filter; click "Repeat (2+) Disputes" to
  narrow every visual on the page to just the high-risk merchants.
- **Merchant Spike Day (one-click, derived)** — repeated from Page 3 here
  since this page's tables are what actually names the spiking merchants.

**Already modeled, available via the Filters pane even without a dedicated
slicer on canvas** (add in one drag if you want them on-canvas too):
`settlement_account_on_file`, `mcc_imputed`, `amount_was_negative` /
`disputed_amount_was_negative`, `merchant_status`, `business_type`.

**Deliberately not added:** an age-band filter on `date_of_birth` — that field
has known bad data (some corrupted birth years), so a derived age slicer would
look broken rather than insightful.

### Turning the always-on slicer rail into a toggleable "Filters" panel with Apply/Reset

The 12 slicers currently sit in an always-visible left rail on every page.
Making that a hide/show panel driven by a **Filters** button, plus dedicated
**Apply**/**Reset** buttons, uses Power BI's **Bookmarks** feature — which is
authored by arranging the report and clicking "Add" in the Bookmarks pane,
not by hand-editing JSON. (The semantic model and every measure/visual in
this project *are* hand-authored text, safely — but bookmarks specifically
capture a live snapshot of visual state that Power BI Desktop generates
internally; writing that by hand is the same category of risk that broke the
project's relationships earlier in this build, for much lower payoff here.)
It's a 5-minute, click-only task:

1. **View ribbon → Bookmarks pane** and **Selection pane** (both toggles).
2. Group the 4 rail slicers on a page (Selection pane, multi-select, right
   click → Group) and name the group `FilterRail`.
3. With `FilterRail` **hidden** (eye icon off in Selection pane), Bookmarks
   pane → **Add** → rename it `Filters Closed`.
4. Show `FilterRail` again, optionally widen the canvas content area to make
   room → Bookmarks pane → **Add** → rename it `Filters Open`.
5. Insert a button (**Insert → Buttons → Blank**), label it "Filters", set
   **Action → Type: Bookmark**, target a new bookmark that just toggles
   between the two above (Bookmarks pane → right-click `Filters Open` →
   "Select as toggle" pairs it with `Filters Closed` automatically in recent
   Desktop versions; otherwise duplicate the button and point one instance at
   each bookmark, stacked in the same spot).
6. **Reset button**: with all slicers in their default (nothing excluded)
   state, Bookmarks pane → **Add** → rename `Reset Filters` → in the
   bookmark's **⋮ menu → Data: on** (so it captures slicer selections, not
   just visibility). Insert a button labeled "Reset", Action → Bookmark →
   `Reset Filters`.
7. **Apply button**: Format pane → page-level **Filters** options → toggle
   **"Apply button for slicers"** on (Options → Report settings, if not
   visible per-page) — this adds a native Apply checkmark to each slicer so
   selections stage before filtering, which is the built-in equivalent of a
   global Apply action.
8. Repeat steps 2–6 once per page (`FilterRail` groups/bookmarks are
   per-page); the button visuals can be copy-pasted across pages.

## 5. Design notes

**Light theme, fintech/cyber-risk accent palette** — matches
`dashboard/template.html`'s color language (electric indigo `#6366F1` / cyber
cyan `#06B6D4` primary; coral crimson `#EF4444` / amber gold `#F59E0B` /
emerald mint `#10B981` semantic status colors) but on a white background
rather than dark, per request. Applied via a custom theme JSON
(`UPI_Fraud_Analytics.Report/StaticResources/SharedResources/BaseThemes/UPIFraudTheme.json`)
so it's one file, not per-visual overrides.

**Card styling** — every visual container carries a rounded-corner (12px),
light-bordered "card" style (`#E2E8F0` border, white background). The 8
fraud/dispute KPI cards (Chargeback Count on Overview; all 4 headline cards
on Fraud & Dispute Analysis) use a **risk-elevation variant** instead: a
crimson (`#EF4444`) border on a light-red (`#FEF2F2`) tint, echoing the HTML
dashboard's glowing-border treatment for at-risk cards. This is a static
style tied to *which cards represent active fraud exposure*, not a live
conditional-formatting rule bound to the current value — a value-driven rule
would need a DAX `FillRule` expression in place of a literal color, which is
meaningfully riskier to hand-author correctly than a fixed color (in the same
risk category as the relationship-endpoint issue hit earlier in this build).
If you want true value-conditional borders (e.g., only glow red when Failed
Rate > 10%), it's a same-page Desktop task: select the card → Format pane →
Effects → Border → the `fx` icon next to Color → "Format by: Rules".

Bar/column charts use `showAllDataPoints` so each category gets a distinct
theme color rather than one flat accent.

**Not portable from the HTML dashboard's design spec, and why:** Power BI
Desktop's visual formatting model has no equivalent of CSS
transitions/animations — there's no hover-lift, staggered fade-in-on-load, or
continuous pulse effect available for native visuals (that's a browser/CSS
capability, not something the report-rendering engine exposes, with or
without hand-authored JSON). The interactive Filters/Apply/Reset panel is
achievable, but only via Bookmarks (§4 above), not as generated files.

## 6. Rebuilding / opening

```bash
python3 scripts/build_powerbi_project.py
```
then open `powerbi/UPI_Fraud_Analytics.pbip` in Power BI Desktop. The
`DataFolder` parameter defaults to this machine's absolute path to
`data/cleaned/`; if you move the project, update it under **Transform data >
Manage Parameters** and hit **Refresh**. The script overwrites files in place
and does not delete the `powerbi/` folder first, so manual additions you make
in Desktop (like the bookmark buttons in §4) survive a rerun as long as
they're saved inside `.Report`/`.SemanticModel` — just don't `rm -rf powerbi/`
before rerunning.
